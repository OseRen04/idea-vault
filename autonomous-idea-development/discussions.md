# 議事録

## 会話URL未登録

### 議題
- 端末監視・ファイル横断取得MCPの検討と方針転換。
- GitHubに保存したアイデアを自律的に開発する仕組みの構想。

### 議論内容
- 最初に「自分が使うすべてのデバイスを監視するMCP」を検討し、次にPowerPoint・PDF・スマホのメモなどを横断的に取得してストレージも最適化する案へ発展した。各PCからのファイル取得には端末側の取得エージェント、アクセス権限、通信経路が必要だと整理したが、ユーザーはこの方向を面白くないと判断し、別のMCP案へ切り替えた。

- 続いて、ユーザーが毎回指示しなくても、ベンチャー企業のようにAIが企画を形にし、深夜に自律開発を進めるエージェントの構想を提示した。既存のAIコーディングエージェントやスケジューラーなどの組み合わせで実現する方向が議論された。

- その後、ユーザーは要件を具体化し、GitHubにpush済みのアイデア一覧をエージェントが確認し、「開発：許可」とされたアイデアを一覧の上から順に選び、規定のワークフローに沿って開発する仕組みを理想として明示した。開発対象の順序と許可判定を通常のプログラムで扱い、AIには要件整理・設計・実装・テストを担当させる構成が提案された。GitHub ActionsやGitHub Agentic Workflowsなどは実行基盤の候補であり、採用は確定していない。開発状態の管理、再開方法、PR作成、公開・マージの承認基準などの細部は未決定。

- ユーザーはIdea Vaultを使ってこのアイデアをGitHubに保存するよう依頼した。保存先として新規の `OseRen04/idea-vault` リポジトリを作成し、企画名はAIに任せ、企画名のフォルダの下に既存の `ideas/autonomous-idea-development/` 構造を置くよう指定した。

### 決定事項
- ユーザーは、端末監視・ファイル横断取得を進める方向から、別の構想へ切り替えた。
- ユーザーは、毎回の指示なしに、GitHubのアイデア一覧から開発を許可した対象を選び、規定のワークフローで開発する仕組みを理想として明示した。
- 当時の開発対象の選択順は「一覧の上から順」とされていた。この検討経緯は履歴として保持する。
- ユーザーの依頼によりアイデアをGitHubへ保存し、保存先に `OseRen04/idea-vault` を作成した。企画名はAIに任せ、企画名のフォルダ内に既存の `ideas/autonomous-idea-development/` 構造を置くよう指定した。これは移行前の配置の経緯を示す。

### 未決定事項
- 実行基盤の採用。GitHub ActionsやGitHub Agentic Workflowsなどは候補であり、確定していない。
- 開発状態と進捗の管理、開発途中の企画の再開方法。
- PR作成、公開・マージの承認基準。
- 通常のプログラムによる順序・許可判定とAIによる開発作業を組み合わせる構成の具体化。

## 会話URL未登録

### 議題
- 自律開発システムの実行基盤と技術ごとの責務。
- GitHub Actions、Symphony、Codexの組み合わせ。
- 自動開発の時間指定、認証、追加費用の抑制。
- 現行Idea Vaultと仕様書の整合、実装順序。

### 議論内容
- ユーザーは、独自Web UIを望まなかった。ChatGPTだけをUIとする方針を明示した。
- 当初は有料クラウド上でSymphonyを動かす構成を検討した。ユーザーは追加費用を理由に有料クラウドを不採用とした。
- ユーザーは、GitHub Actionsを実行基盤とする方式を提案した。ユーザーはSymphonyの採用も維持した。
- GitHub Actionsは、指定時刻に処理を起動する。Symphonyは、Issueを取得してCodexの作業を統括する。Codexは、設計・実装・テストを担当する。
- ユーザーは、開発対象のリポジトリ自体が存在しない点を指摘した。初回実行では、GitHub CLIがPrivateリポジトリ、初期ファイル、Issueを準備する必要がある。
- GitHub CLIは既存の公式ツールである。独立した造語や独自コンポーネント名を追加しない方針が示された。
- ユーザーは、開発スケジュールをユーザー単位で管理すると決めた。ユーザーは、ChatGPTで曜日と時間帯を指定する。
- CodexにはChatGPT契約による認証を用いる方針を検討した。追加API従量課金を避けることが重要な要件となった。
- 一方、GitHub Actions上のCodex無人認証は未検証である。認証更新、安全な資格情報保存、失効時の停止が課題として残った。
- Symphonyは継続稼働を想定した仕組みである。GitHub Actionsでの停止、進捗保存、翌日の再開は追加検証が必要とされた。
- 現行Skillの原本は、リポジトリ直下の企画フォルダに3ファイルを置く。旧仕様書の `ideas/<id>/` と2ファイル構成は更新対象とされた。
- 独自の `projects.json` と実行用Privateリポジトリの分離は提案された。ただし、両方とも採用は未決定である。
- ユーザーは、「反論」は批判ではなく、事実確認と実現方法の検討だと明示した。実装順序は検証結果に基づいて決める方針となった。

### 決定事項
- ユーザーは、ChatGPTを唯一のユーザー向けUIとする。
- ユーザーは、Idea VaultとGitHubで企画を管理する。
- ユーザーは、GitHub Actionsを定期実行の基盤として採用する。
- ユーザーは、SymphonyによるCodexの実行管理を採用する。
- ユーザーは、企画専用のPrivateリポジトリとIssueを自動作成する方式を求める。
- ユーザーは、自動開発の時間設定をユーザー単位とする。
- ユーザーは、有料クラウド基盤と独自Web UIを採用しない。
- ユーザーは、追加API従量課金のない構成を目標とする。
- ユーザーは、造語を用いずに技術名と処理内容を明示するよう求めた。

### 未決定事項
- ChatGPT契約によるCodexの無人認証が実際に成立するか。
- Codexの認証情報を安全に保管・更新する方式。
- GitHub ActionsとSymphonyの安全停止・再開方式。
- 認証用Actionsの配置先とGitHubの権限付与方法。
- GitHubの情報だけで開発状態を復元できるか。
- 企画の開発完了基準とレビュー手順。

### 次のアクション
- Skillと仕様書のフォルダ構造および企画書形式を一致させる。
- 非公開の検証環境でCodexの無人認証を確認する。
- Symphonyが既存IssueからCodexを起動できるか確認する。
- GitHub CLIでPrivateリポジトリとIssueの初期構築を検証する。
- 保存・停止・再開の試験後にGitHub Actionsの定期実行を有効にする。
